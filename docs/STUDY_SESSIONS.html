The Big Picture

"My project is two separate programs: a React frontend that runs in the browser, and an Express + MongoDB backend that runs on a server. They don't share any code — they only talk to each other over HTTP, exchanging JSON."

The two halves

client/ — React frontend, runs in the browser. Shows pages, buttons, cards; asks the backend for data.

server/ — Express backend, runs on a server machine. Receives requests, runs logic, talks to the database, sends answers back.

The 3 route groups (app.js)

app.use('/api/auth',     ...)   // register, login, profile
app.use('/api/progress', ...)   // the memorization plan (the heart)
app.use('/api/chat',     ...)   // the AI assistant

app.js vs server.js

server.js — "start the engine." Connects to MongoDB, then app.listen(PORT). ~15 lines. No routes/logic defined here.

app.js — "assemble the app." Security middleware (cors, helmet, compression), the 3 route groups, the 404 catch-all. Exports the finished app for server.js to run.

app.js builds the app. server.js runs it. Split this way so app.js can be tested without a real DB connection or open port.

Routes in app.js vs routes file

app.js routes by prefix only: "anything starting with /api/progress → hand off to progressRoutes.js." It's the building directory sign.

progressRoutes.js defines the specific endpoints and which controller function handles each: router.get('/today', getTodayTasks). These are the actual office doors.

Full URL = prefix (app.js) + path (routes file): /api/progress + /today = /api/progress/today.

The Data Models

Vocabulary: collection = like a table. document = one record (a JSON object). schema/model = the blueprint for what fields a document has.

1. User — one doc per person

FieldMeaning
name, email, passwordCredentials
dailyNewPagesGoal: pages/day (0.5–10)
currentStreakConsecutive active days
lastActiveDateLast active day — streak math compares to this
onboardingCompleteFinished initial setup?
planStartDateWhen the plan began — separates "already knew" vs "learned in-app"
reviewIntensitylight / standard / strong
offDaysWeekday rest days

2. UserProgress ⭐ — one doc per (user, page) pair

A user with 200 memorized pages has 200 of these documents.

FieldMeaning
userIdOwner (User._id)
pageNumber1–604
status'memorized' / 'not_started'
memorizedDateFirst memorized
lastReviewedDateDrives the whole review schedule
reviewCountTimes reviewed

Q: Why one document per page instead of an array on the User?

  1. Scheduling needs per-page history (dates, counts) — naturally one record per page
  2. Database can sort/index efficiently (e.g. by lastReviewedDate, oldest-first)
  3. Marking one page = updating one tiny doc, not rewriting a 600-element array
  4. Unique index on {userId, pageNumber} — DB itself blocks duplicates

3. QuranMetadata — the reference table

Static, same for every user. 604 docs, one per page: juzNumber, surahName. No Quran text — just labels. Seeded once via node seed/quranData.js.

How they relate

User (1) ──────< UserProgress (many)    QuranMetadata (shared)
  _id            userId → User._id          pageNumber
                  pageNumber ── matched by page number ──┘

Streak: does it need ALL tasks done?

No — any single task (new OR review) is enough. The streak is a daily on/off flag via lastActiveDate, not a task counter:

!lastActiveDate           → streak = 1   (first ever)
lastActiveDate === today  → unchanged    (already counted today)
isStreakContinued()       → streak + 1   (came back next day, or only off-days in gap)
otherwise                 → streak = 1   (real day missed → reset)

Doing 1 task or 10 tasks today has the same effect on the streak — the first one already locked the day in.

Custom / fixed review count

If the user sets recentReviewCount / cycleReviewCount on Settings ("Fixed number" mode), the automatic reviewIntensity formula is skipped entirely and that exact number is used instead. null = "use the automatic formula."

What is the user's unique ID?

It's _id — auto-generated by MongoDB (a 24-char ObjectId), not the email. UserProgress links to its owner by storing that same User._id in its userId field — that's the connection between the two collections. Email is unique too, but only used for login, not internal linking (since email could theoretically change, _id never does).

✅ You can now explain

  • The 3 models and what each field is for
  • The "one doc per page" design decision and its 4 reasons
  • Streak = daily flag, not task counter; any 1 task is enough
  • Custom review overrides bypass the formula
  • _id (not email) is the real linking key between collections
Session 3 / 7

Authentication

Two problems: (1) Storage — never keep passwords readable. (2) Sessions — prove who you are on every request without retyping a password.

Part A — Passwords (bcrypt)

Hashing = scrambling into a fixed jumble, irreversible. Salted = random data mixed in so identical passwords get different hashes.

stored in DB:   hash("MySecret" + salt) → $2a$10$abc...
login attempt:  hash("MySecret" + same salt) → $2a$10$abc...  ✅ match!

Never decrypted — only re-hashed and compared. password field is also marked select: false so it's never returned by normal queries.

Passwords are hashed with bcrypt at salt strength 10 before saving. We store only the hash, never plaintext; login verifies by hashing the attempt and comparing. bcrypt is one-way and salted, so passwords can't be recovered even if the DB leaks.

Part B — Staying logged in (JWT)

A JWT = a tamper-proof "wristband": contains your _id + expiry (30 days), digitally signed with a server secret. Signed = the server can verify it issued it, without storing any session.

LOGIN: password ok → server signs JWT (your _id) → sent to browser
BROWSER: saves token in localStorage
EVERY REQUEST AFTER: browser attaches token → server verifies → "yep, user X"

The full journey

  1. Register — reject if email exists → create user (bcrypt hook hashes password) → sign JWT → return token + safe fields (never password)
  2. Login — find user with .select('+password') → matchPassword() via bcrypt.compare → sign fresh JWT. Error message is deliberately vague ("Invalid email or password") so attackers can't tell which emails exist.
  3. Browser stores & attaches — AuthContext saves token to localStorage; an axios interceptor in api.js auto-attaches it to every request: 
    API.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});
    A response interceptor wipes the token and redirects to /login on any 401 — self-healing expired sessions.
  4. Server guards routes — protect middleware reads the header, runs jwt.verify() (checks signature + expiry), attaches the user to req.user. router.use(protect) in progressRoutes.js turns this on for every progress route at once.

Data isolation: every protected controller queries using req.user._id — e.g. UserProgress.find({ userId: req.user._id }). Structurally impossible to fetch someone else's data.

✅ You can now explain

  • bcrypt: one-way + salted, hash-compare, select:false
  • JWT: signed wristband, no server-side session
  • Full flow: register/login → interceptor attaches → protect verifies → req.user._id isolates data
Session 4 / 7

The Core Engine ⭐ (getTodayTasks)

Every dashboard load asks: "What should this user do today?" Answer = new pages + review pages. Built entirely by getTodayTasks in progressController.js.

The science (the "why")

Ebbinghaus's Forgetting Curve (1885): new material fades fast at first, then more slowly. Spaced repetition (Pimsleur 1967, Leitner 1972): reviewing at the right moments resets the forgetting clock, so retention lasts longer with less effort.

BucketWho's in itWhy
Recent reviewPages memorized in last few active daysFreshest = most fragile → review often
Cycle reviewEverything olderStable → slower rotation, oldest-reviewed-first
Honest caveat: this approximates "true" spaced repetition (like Anki's SM-2, where each item gets its own growing interval). This app uses a set-wide rotation speed instead. A defensible simplification — and reviewCount + lastReviewedDate are already stored per page, exactly what a per-item algorithm would need next.

A) Dates: always UTC YYYY-MM-DD strings

const getDateString = (date) => new Date(date).toISOString().split('T')[0];

Avoids "today" flipping at the wrong moment depending on server location.

B) Off days

If today is an off day → empty task lists, isOffDay: true. But if the streak is alive, lastActiveDate still advances — a rest day doesn't break the chain.

C) Load the raw material

UserProgress.find({ userId, status: 'memorized' })
  .sort({ lastReviewedDate: 1, pageNumber: 1 });

This sort alone puts the stalest-reviewed pages first — the engine behind "review what's closest to being forgotten first."

D) How many NEW pages today (the fractional-goal trick)

const assignedToday     = Math.ceil(dailyNewPages * (daysPassed + 1));
const assignedYesterday = Math.ceil(dailyNewPages * daysPassed);
return Math.max(0, assignedToday - assignedYesterday);

Example with dailyNewPages = 0.5:

DayassignedTodayassignedYesterdaytoday's new pages
0101
1110
2211
3220

→ 1,0,1,0... = "a page every other day," with one formula handling whole and fractional goals identically. New pages are picked walking 1→604 in order, first not-yet-memorized pages. Skipped for paused users or a Hafiz (all 604 done).

E) How many REVIEWS today

if (totalMemorized === 0) return 0;
if (totalMemorized === 604) { /* Hafiz schedule */ }
if (totalMemorized < 3) return totalMemorized;
const cycleDays = { light: 14, standard: 10, strong: 7 }[reviewIntensity] || 10;
return Math.min(Math.ceil(totalMemorized / cycleDays), 40);

100 memorized pages, standard (cycleDays=10) → 10 pages/day → whole set cycles roughly every 10 days. light = slower (14d), strong = faster (7d). Capped at 40/day. Skipped if a fixed override (cycleReviewCount) is set.

F) Splitting recent vs cycle — no duplicates

Last 3 active days' pages → recent pool (capped at max(3, min(ceil(dailyNewPages×3), 6)) or manual override). Everything else memorized → cycle pool, explicitly excluding recent-pool pages. A page never appears in both lists.

G) Labeling — one batched query

QuranMetadata.find({ pageNumber: { $in: pageNumbers } });

One query for all chosen pages, not one per page — a real performance detail (relevant to the <3s load requirement).

Completing a task → streak tick

type: 'new' → creates/updates UserProgress as memorized, sets memorizedDate. type: 'review' → sets lastReviewedDate, bumps reviewCount. Then the streak rule from Session 2 fires.

buildProgressSummary — same logic, read-only

A smaller function mirroring the same new-page/review rules but returning only counts, with no writes — small enough to feed the AI chatbot real context. Same business logic, reused in two places (DRY).

✅ You can now explain

  • The two-bucket review system + the science (Ebbinghaus + spaced repetition)
  • UTC date-string trick
  • The fractional new-page formula and why it elegantly handles 0.5/day
  • The review-target formula (totalMemorized / cycleDays, capped at 40)
  • buildProgressSummary reuses this logic for the AI assistant

Frontend Structure

Routing — App.jsx

<ThemeProvider>      // dark/light mode
  <AuthProvider>      // who is logged in
    <ToastProvider>   // popup notifications
      <Router>...<Routes>...</Router>

Public routes (/, /login, /register) — wrapped in PublicRoute, redirects already-logged-in users away. Protected routes (/dashboard, /onboarding, /settings, /progress, /library) — wrapped in ProtectedRoute, shows a spinner while checking auth, bounces to /login if no user. Wrappers also force onboarding if onboardingComplete === false.

Auth state — AuthContext.jsx

A React Context = an app-wide shared box of state, readable from any component without manually passing it down. Exposes user, loading, and login/register/logout/updateUser. On first load, checkAuth() calls GET /api/auth/me if a token exists — this is why refreshing the page keeps you logged in. Any component reads it via useAuth().

Dashboard.jsx — the pattern every page follows

fetch → store in state → render from state.

const [taskRes, juzRes] = await Promise.all([
  progressAPI.getTodayTasks(),
  progressAPI.getJuzProgress(),
]);

Promise.all fires both requests in parallel instead of one after another — faster, relevant to the <3s load requirement.

Optimistic UI

await progressAPI.markComplete({ pageNumber, type });
setCompletedKeys(prev => new Set(prev).add(`${type}-${pageNumber}`));

The card flips to "Done" immediately, locally, with an Undo option — instead of waiting for + re-fetching from the server. Assume success, update instantly, reconcile only if it actually fails. Makes the app feel instant.

Session 6 / 7

Features: Library, Tours, Progress, AI

Library reader & Memorize mode

Memorize mode is not a separate page — it's a URL flag: ?mode=memorize. Why: survives a refresh, is bookmarkable, and reuses all existing reader machinery (audio, verse selection, tafsir panel, RTL layout) unmodified — no second component to maintain.

"Test myself" conceals words behind a blur until tapped — this is active recall: forcing retrieval cements memory better than re-reading. Blurred (not hidden) so the line's shape stays visible as a positional cue.

Onboarding & guided tours

driver.js draws a dimmed spotlight overlay around one element at a time. Tours run on first visit only, gated by a localStorage flag (e.g. seenDashboardTour). Each tour filters out steps for UI that doesn't exist for that user (e.g. a Hafiz has no "new memorization" column, so that step auto-skips).

Progress page

30-Juz grid in two densities (compact/detailed), compact is default to avoid clutter. Also a GitHub-style contribution graph from memorizedByDate — all date math in UTC, consistent with the backend's date-string discipline.

The AI Assistant — chatController.js

Powered by Groq's llama-3.3-70b-versatile. Knows the user's real progress — before calling the AI, the server calls buildProgressSummary(req.user) (the same function from Session 4) and injects real streak/pages/tasks into the prompt, instructing the model never to invent numbers. If that lookup fails, chat still works without personalized context (fails safe). Rate-limited to 20 requests/5 min per user.

Quran content itself

The app stores no Quran text or audio — pulled live from public APIs (api.alquran.cloud for text with full tashkeel/diacritics, cdn.islamic.network for audio). Responses cached in-memory (Maps) so revisiting a page is instant.

  • Active recall via blur-based self-testing

  • External Quran content APIs + client-side caching
Session 7 / 7

Defense Prep — Q&A + 60-Second Summary

Memorize this — say it almost verbatim

"It's a React frontend and an Express/MongoDB backend that talk over a REST API with JWT auth — passwords bcrypt-hashed, tokens attached by an axios interceptor and verified by a protect middleware. The data model is one document per user-page, which records when each page was memorized and last reviewed. The core engine, getTodayTasks, turns that history into a daily plan: new pages up to the user's goal, plus two review buckets — recent pages reviewed often, older pages cycled oldest-first — which operationalizes the Ebbinghaus forgetting curve and spaced repetition. All dates are compared in UTC to stay timezone-safe, rest days preserve the streak, and Quran text/audio plus an AI assistant that's aware of the user's real progress round out the experience."

Rapid-fire Q&A

Q: Why MongoDB, not SQL?

Data is document-shaped, access is mostly "load everything for this user." Schema evolved a lot during development (off-days, pause mode, overrides added later) — MongoDB's flexibility made that cheap.

Q: Why one UserProgress doc per page, not an array on User?

Per-page history needs sorting/filtering by page — exactly what an indexed collection gives. One small doc update per tap, not rewriting a 600-element array. Unique index blocks duplicates at the DB level.

Q: How does review scheduling map to the forgetting curve?

Fresh pages decay fastest → reviewed often (recent bucket). Older pages are more stable → rotated slower (cycle bucket), oldest-reviewed-first as a stand-in for "review right before it'd be forgotten."

Q: Is this "real" spaced repetition like Anki?

Honestly, no — Anki/SM-2 gives each item its own growing interval; this uses a set-wide rotation speed plus a recent-window heuristic. Faithful to the principle; reviewCount + lastReviewedDate are already stored per page for a future per-item algorithm.

Q: How are passwords stored?

bcrypt hash, salt strength 10, select:false so never returned by default queries, verified with bcrypt.compare — never reversed.

Q: How is session security handled?

JWT signed with a server secret, 30-day expiry, sent as a Bearer token, verified by protect middleware on every protected route.

Q: How are timezones handled?

Every date reduced to a UTC YYYY-MM-DD string before comparison — avoids "today" shifting by server location. Trade-off: day rolls over at UTC midnight, not the user's local midnight — acceptable now, fixable later with a per-user timezone field.

Q: How would you scale it?

Per-user queries already indexed; API is stateless (JWT, no server sessions) so it scales horizontally; QuranMetadata is tiny/static and cacheable; heavy Quran text/audio served by external CDNs, not your server.

Q: What happens when someone finishes the whole Quran (Hafiz)?

totalMemorized === 604 → no new pages assigned, review target switches to a Hafiz-specific schedule, dashboard shows a congrats banner instead of a "new memorization" column.
