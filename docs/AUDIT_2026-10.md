## 1. Executive summary

### Verdict: **not launch-ready yet — but close, and the gap is specific.**

The codebase is unusually careful for its size and age: authorization is scoped to the
caller on every route (an IDOR sweep of every `:id` route found nothing), NoSQL-operator
injection is closed by a central type gate, there are no HTML-injection sinks anywhere in
the client, third-party tafsir HTML is converted to text, the open-redirect guard held
against every payload in a real browser, and the reader's engineering (fonts, prefetch,
audio) is measured and bounded. The problems are concentrated in a short list:

**Blocks a public launch (fix first):**
1. **C-01 — One unauthenticated request can freeze the whole API for minutes to hours.**
   The email regex in the User model backtracks exponentially; a 33-character email
   blocked every other request for 4.7 s on the isolated stack, and each 2 extra
   characters multiply that by ~4. *CONFIRMED.*
2. **H-01 — Deleting an account leaves the user's notes, highlights, drawings and
   bookmarks in the database**, contrary to the "all associated data" promise. *CONFIRMED.*
3. **H-02 — A single failed request can silently wipe a user's entire memorization
   record** (reproduced: 40 pages → 0 after one 500 and a tick-untick), and the same
   replace-on-stale-state pattern exists in Settings and in the ink layer. *CONFIRMED.*
4. **H-03 — On the half-page plan, "Mark All" and "Want more" record the whole page.**
   *CONFIRMED.*
5. **H-04 / H-05 — Legal readiness:** third-party Quran fonts and a full-text derived
   dataset are committed to a **public** GitHub repo with no licence or attribution; there
   is no privacy policy or terms (the links are `href="#"`), while user data goes to Groq,
   Google Fonts and five content CDNs. *LIKELY / CONFIRMED.*
6. **H-06 — No password reset**: a user who forgets their password loses the account
   permanently (known, still open in the plan's Part 4).

### Risk statement for a non-technical owner

Today, anyone on the internet could take the app offline for hours with one carefully
typed sign-up attempt, and a user on a weak phone connection can lose their whole
memorization history by tapping a page twice. Both are small, well-understood fixes. Beyond
those, the app is not yet legally ready for strangers: it has no privacy policy, it sends
some personal data to outside services without saying so, it keeps data it promises to
delete, and it redistributes fonts and Quran data whose owners have not been asked. None of
this reflects careless engineering — the security fundamentals are solid — but these items
must be closed before the app is announced publicly. Once the "Now" list in §6 is done
(roughly 2–3 focused sessions plus some emails), the app is in good shape for a soft launch.

## 3. Strengths (what is genuinely well done)

- **Authorization is right everywhere.** Every query is scoped to `req.user._id`, foreign
  and malformed ids both answer 404 (no id probing). A full IDOR sweep with a second user
  against bookmarks, annotations (note/highlight/drawing/text), to-dos and every list
  endpoint found **no** cross-user read or write ([Appendix B](audit/tool-outputs.md#idor-results)).
- **Injection surface closed by design.** `middleware/validate.js` rejects objects and
  arrays where scalars are expected; login `{ "$gt": "" }`, query `page[$gt]=0`, and
  operator objects inside batch ops all returned 400. Mass-assignment attempts
  (`email`, `currentStreak`, `onboardingComplete`, foreign `userId`/`_id` in `/todos/restore`
  and `/annotations/batch`) were ignored — controllers build documents from whitelisted
  fields.
- **The annotation batch endpoint** (`annotationController.js:392-558`) is a model of
  careful API design: state-keyed idempotent ops, strict per-field validation, cap check
  before writing, and snapshot rollback on partial failure — with a fault-injection test.
- **No HTML sinks in the client.** No `dangerouslySetInnerHTML`/`innerHTML` in `src/`;
  hefzmoyaser HTML is reduced to text (`quranApi.js:285-297`); chatbot links pass an exact
  path/parameter allow-list (`utils/chatLinks.js`). Stored XSS payloads in bookmark labels,
  notes, text notes, to-dos, the display name and the account name rendered as inert text
  on every page (browser-verified).
- **Open redirect is closed in practice.** Twelve `returnTo` payloads (absolute,
  protocol-relative, backslash, `/.//`, `%2e`, encoded, `javascript:`, tab) all landed on
  `/dashboard` in a real browser, both after the login form and through the signed-in
  `PublicRoute`.
- **Public Library is genuinely public.** Logged out, `/library` made **zero** API calls and
  never bounced to `/login`; the 401 interceptor ignores token-less requests by design.
- **Password change revokes older sessions** (`passwordChangedAt` + `iat` check) — the right
  instinct (see M-04 for the UX gap).
- **Reader engineering is measured, bounded and documented:** LRU-capped page data and font
  faces (`mushafApi.js:53-54, 373`), idle-time priming, prefetch that honours Save-Data/2g,
  a retrying, fallback-capable gapless audio pipeline, wall-clock cross-tab timer with Web
  Locks. Comments explain *why* with measurements.
- **Server tests are real integration tests** (166, in-memory Mongo, no network, no dotenv),
  with IDOR tests for every `:id` route and a byte-exact rollback test.
- **Data you can trust:** the committed structure data was measured correct (6,236 verses,
  240 rub boundaries, 114 surahs, monotonic juz/hizb), and the search-index generator fails
  closed on any glyph-position mismatch.
- **Security headers on the API** (helmet defaults incl. CSP/HSTS/nosniff), connect-then-
  listen boot, env assertion, generic 500s in production, lint clean, i18n key parity.

### Critical

#### C-01 · Unauthenticated ReDoS in the registration email validator
- **Category:** Security — availability · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** `server/models/User.js:17-19`
  ```js
  match: [
    /^\w+([.-]?\w+)*@\w+([.-]?\w+)*(\.\w{2,3})+$/,
  ```
  `([.-]?\w+)*` is a nested quantifier with an optional separator, so a non-matching input
  like `aaaa…a!` has exponentially many ways to split. It runs on every
  `POST /api/auth/register` (`authRoutes.js:32` → `authController.js:32 User.create`); the
  only gates before it are the type check and a `findOne`. There is no length cap on
  `email`. Measured on the isolated stack over HTTP (concurrent `GET /health` latency in
  brackets):

  | Email length | Register request | `/health` waited |
  |---|---|---|
  | 25 | 28 ms | 1 ms |
  | 29 | 294 ms | 244 ms |
  | 31 | 1,161 ms | 1,130 ms |
  | 33 | 4,666 ms | 4,636 ms |

  Growth is ×4 per 2 characters, so ~41 characters ≈ 20 minutes of a frozen event loop per
  request. Node cannot interrupt a running regex; a proxy timeout only drops the client.
- **Impact:** The API is one Node process. One unauthenticated request from anyone (the
  regex is public on GitHub) freezes every user's requests; the auth limiter
  (10 / 15 min / IP) still allows ~10 such requests per window, i.e. a permanent outage
  from a single IP. Render has no health check configured (`render.yaml`) to even restart it.
- **Recommendation:** Replace the pattern with a linear one (e.g. the WHATWG
  `input[type=email]` regex, or simply `^[^\s@]+@[^\s@]+\.[^\s@]+$`) **and** add
  `maxlength: 254` plus a controller-side length check before any validation; trim and
  lower-case first. Add a regression test that `a`×50+`!` returns 400 in < 50 ms. Consider
  running Node with `--enable-experimental-regexp-engine-on-excessive-backtracks` as
  defence in depth.
- **Related:** M-02 (the same regex rejects valid addresses), M-06 (abuse controls).

### High

#### H-01 · Account deletion leaves personal data behind
- **Category:** Privacy / data lifecycle · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** `server/controllers/authController.js:442-444`
  ```js
  await UserProgress.deleteMany({ userId });
  await Todo.deleteMany({ userId });
  await User.findByIdAndDelete(userId);
  ```
  `Bookmark` and `Annotation` are never touched; there is no cascade hook. Reproduced:
  per-collection counts for the user before → after `DELETE /api/auth/account` were
  `Bookmark 1 → 1`, `Annotation 3 → 3` (note, highlight, drawing). The leaderboard cache is
  not cleared either: the deleted user's display name was still served by
  `GET /api/leaderboard` immediately afterwards (up to the 5-min TTL). The UI promises
  "permanently delete your account and all associated data" (`en.json:351`). The only
  cascade test checks to-dos only (`tests/todos.test.js:240-247`).
- **Impact:** Free-text notes and drawings outlive the account — a right-to-erasure failure
  (GDPR Art. 17-style) and a trust problem. Not exposed to other users (orphans have no
  owner and ObjectIds are not reused), so this is retention, not leakage.
- **Recommendation:** Delete from every user-keyed collection (Annotation, Bookmark,
  UserProgress, Todo) then the User, ideally in a transaction; `leaderboardCache.clear()`.
  Add a test that iterates `mongoose.modelNames()` and fails if any model with a `userId`
  path still holds rows for the deleted user. One-off cleanup script for existing orphans.
  Consider requiring the current password to delete.
- **Reconciliation:** already logged by the planning session on 2026-10-21 and left for
  this audit to rank; confirmed and ranked High.

#### H-02 · Stale or failed reads + "replace everything" writes wipe user data
- **Category:** Data integrity / swallowed errors · **Confidence:** CONFIRMED (a) · LIKELY (b–e) · **Effort:** S (guards) / M (delta APIs)
- **Root cause:** a failed or stale load is indistinguishable from "empty", and the next
  write replaces the server's whole set with the client's view.
- **Variants:**
  - **(a) Library untick — CONFIRMED.** `Library.jsx:895-906` swallows a failed
    `GET /progress/all` (`.catch(() => { landOn(1); })`), leaving `memorizedPages` empty.
    Unmarking sends the whole client set (`Library.jsx:3502`
    `progressAPI.updateMemorized({ memorizedPages: Array.from(nextPages) })`), and the
    server deletes every page not in it (`progressController.js:1126-1130`
    `deleteMany({ ..., pageNumber: { $nin: ... } })`). **Reproduced in Chrome:** a user with
    40 memorized pages; the first `/progress/all` returned 500; ticking then unticking page
    100 left **0** memorized pages, with a success toast and no undo.
  - **(b) Stale tab — LIKELY.** Same path with no failure at all: pages marked on the
    Dashboard or another device after the Library loaded are deleted on the next untick.
  - **(c) Settings editor — LIKELY.** `Settings.jsx:840-847` swallows the same load
    (`.catch(() => {})`); `?edit=1` opens the editor before it resolves; the save is a full
    replace (`Settings.jsx:247`). `onSave` also never refreshes `partialPages`
    (`Settings.jsx:1854-1860`) and "Reset progress" never refreshes local state, so a second
    save can restore or corrupt pages.
  - **(d) Ink overwrite — LIKELY.** `Library.jsx:2787-2789` turns a failed annotations GET
    into `[]`; a page with unsaved strokes is never reseeded (`Library.jsx:3136-3146`); the
    server replaces strokes wholesale (`annotationController.js:364 $set: { strokes }`). A
    stroke drawn before (or after a failed) load erases the page's saved ink.
  - **(e) Lost writes — LIKELY.** A failed ink save clears the dirty set before the request
    and never retries (`Library.jsx:3082-3095`); the unmount flush swallows errors
    (`:3402`); a note draft is discarded on every page turn, including audio-driven turns
    (`Library.jsx:3075`).
- **Impact:** Irreversible loss of a user's memorization history (dates, review counts) or
  drawings from one flaky request on mobile — the core asset of the app.
- **Recommendation:** (1) Track load state; disable mark/edit controls until loaded, and
  show an error + retry instead of an empty state. (2) Replace the Library untick with a
  per-page delta (`PUT /progress/units {action:'remove', unit:'page'}` already exists).
  (3) Make `PUT /progress/memorized` require an explicit `confirmRemoval` (or a version /
  `updatedAt` precondition) and refuse to delete more than N pages without it. (4) Drawings:
  per-page "loaded" flag, keep the old cache on error, and an ETag/version precondition on
  save; re-queue failed saves; flush on `pagehide`. (5) Keep note drafts across turns.
- **Related:** M-14 (swallowed errors), L-11.

#### H-03 · Half-page plan: "Mark All" and "Want more" credit the whole page
- **Category:** Data integrity · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** the single card passes the segment (`Dashboard.jsx:157`
  `onComplete(page.pageNumber, type, page.segment)`), but `markAllNew` drops it
  (`Dashboard.jsx:587` `newPending.forEach(p => markComplete(p.pageNumber, 'new'))`) and so
  does `ExtraTaskCard` (`Dashboard.jsx:218` `onComplete(pageNumber, type)`). Without a
  segment the server takes the whole-page branch (`progressController.js:712-716`,
  `segments: []`). Completion state is keyed by page, not segment (`Dashboard.jsx:468`), so
  both halves of one page collide in "Want more". **Reproduced in Chrome** on a 0.5
  pages/day account: today's task was page 4 verses 2:17–2:20 (first half); after "Mark
  All", `/progress/all` reported page 4 as a **full** page with no partial segment.
- **Impact:** The second half is never assigned; progress %, review queue, estimates and
  leaderboard are silently inflated — the half-page plan's core promise breaks.
- **Recommendation:** Pass `p.segment` in `markAllNew` and `ExtraTaskCard`; key completion
  by `${type}-${pageNumber}-${segment?.half ?? 'full'}`; on the server reject a `type:'new'`
  completion for a half-plan user without a segment, or a malformed `segment` (today it
  silently falls through to whole-page, `progressController.js:689`).

#### H-04 · Licensing: third-party Quran assets redistributed from a public repo; unpermissioned runtime sources
- **Category:** Licensing & legal · **Confidence:** LIKELY (not legal advice) · **Effort:** M (+ emails)
- **Evidence** (full sourcing in [`audit/notes/licensing.md`](audit/notes/licensing.md)):
  - 604 QCF v1 page fonts + `UthmanicHafs1Ver18.woff2` + `sura_names.woff2` are committed
    under `client/public/fonts/` in the **public** repo `github.com/ahmedelhappy/quran-tracker`,
    which has **no LICENSE**. The QCF fonts' embedded name table reads "King Fahad Complex,
    All rights reserved." The only written permission found (Quran Foundation developer
    terms) allows bundling fonts "only as an integrated part of the Application. They may not
    be offered separately" and requires an active Developer Console account and credit.
  - The KFGQPC Hafs font's EULA requires the licence to accompany the file; it does not.
  - `client/public/data/search-index.json` (the whole Quran, word by word, from quran.com
    `text_imlaei`) is committed and publicly served; QF terms forbid storing QF content
    beyond a week outside Content Sync and "build-time bundles".
  - At runtime the reader depends on the unauthenticated legacy `api.quran.com/api/v4`
    (QF's current API requires OAuth client credentials); Aysar at-Tafasir is fetched from
    `newapi.hefzmoyaser.net`, the private backend of another product, with no published
    terms; everyayah.com publishes no licence; `en.sahih` (Daily Verse) is non-commercial
    upstream.
  - Attribution shown in the app: none (`Footer.jsx`, `About.jsx`).
- **Impact:** Takedown or access revocation risk for the core reader; commercial use is not
  covered for several assets; a public repo makes the fonts "offered separately".
- **Recommendation:** Make the repo private or move fonts/index out of it (QF's documented
  font CDN is the recommended runtime source); add `LICENSE` + `THIRD_PARTY_NOTICES.md`;
  ship the KFGQPC EULA next to the font; add an "Acknowledgements & sources" section
  (suggested text in the licensing notes); register a QF Developer Console project and plan
  the move to the authenticated API through a small backend proxy; email KFGQPC, QF,
  Hefz Moyaser and everyayah for written permission; pin or mirror tafsir sources.

#### H-05 · No privacy policy or terms; undisclosed third-party processing
- **Category:** Privacy & compliance · **Confidence:** CONFIRMED (static) · **Effort:** M (content) / S (code)
- **Evidence:** `Landing.jsx:458-461` — Privacy, Terms and Contact are `href="#"`; no
  `/privacy` or `/terms` route exists (`App.jsx`). Data flows observed in the browser and in
  code: every page loads Google Fonts (`index.css:1-2`, IP + UA to Google); the reader sends
  page/ayah/reciter choices to api.quran.com, cdn.islamic.network, everyayah.com,
  cdn.jsdelivr.net and newapi.hefzmoyaser.net; the chatbot sends the user's **name**,
  progress and messages to Groq in the US (`chatController.js:53, 143-152`). The personal
  developer email is published in `Footer.jsx:13` and `About.jsx:89`.
- **Impact:** Public launch without a policy is a legal (GDPR/UK-GDPR, app-store) blocker;
  Groq's terms (§6.2) make the customer warrant that notices and consents exist; the app is
  likely used by minors.
- **Recommendation:** Publish bilingual privacy policy + terms (data held, retention,
  deletion, processors: Render, Atlas, Vercel, Groq, Google Fonts, the CDNs); self-host
  Google Fonts; drop the name from the chat prompt and enable Groq Zero Data Retention;
  decide an age policy; use a project contact address.

#### H-06 · No password reset or email verification
- **Category:** Product / account security · **Confidence:** CONFIRMED (no route) · **Effort:** M
- **Evidence:** no reset/verify routes in `routes/authRoutes.js`; listed as S5 (High) in the
  plan's Part 1 and still open in Part 4 ("pick an email provider").
- **Impact:** A forgotten password permanently loses years of memorization history; with no
  email verification anyone can register someone else's address (blocking them).
- **Recommendation:** Choose the email provider (Resend/Postmark/SES); add time-limited,
  single-use, hashed reset tokens; verify email on signup. Re-issue the JWT on reset.

### Medium

#### M-01 · Page numbers are not validated: out-of-range and fractional pages are stored
- **Category:** Data integrity / leaderboard integrity · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** onboarding upserts whatever numbers arrive (`progressController.js:423-445`,
  no range/integer check, no size cap); `markPageComplete` checks only
  `!pageNumber || pageNumber < 1 || pageNumber > 604` (`:676`); `updateMemorized` filters
  `n >= 1 && n <= 604` but not integers (`:1124`). Upserts skip schema `min/max`
  validators. `pageFraction` returns 1 for unknown pages (`segments.js:236`). Reproduced:
  onboarding with `[99999, -5, 0, 1.5, 700, 2.25]` → 200, all stored; `complete` with 1.5,
  2.5, 3.5, "4.5" → 200; `memorized` `[10.1 … 10.4]` → 4 "pages"; a 2,000-element onboarding
  array → 200 in 473 ms; the account then ranked **#1 with 2,004 pages** on the leaderboard.
- **Recommendation:** Require integers 1..604 everywhere (`Number.isInteger`), dedupe and cap
  arrays at 604, run validators on upserts (`runValidators: true`), reject unknown pages in
  `pageFraction`. One-off cleanup query for invalid rows. Add `segment` to the type gate.

#### M-02 · Registration rejects valid emails and returns 500 for every validation error
- **Category:** Correctness / API · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** the C-01 regex rejects `first+tag@gmail.com` and `me@example.info` (any TLD > 3
  letters). Mongoose `ValidationError`s go to `serverError` → **500**
  (`authController.js:54-56`); outside production the raw message is returned. Reproduced:
  missing name → 500, short password → 500, `+tag` → 500. The test only asserts
  `notEqual(201)` (`tests/auth.test.js:24-25`).
- **Recommendation:** Validate in the controller (or map `ValidationError` → 400, E11000 →
  409); fix the regex (C-01); assert exact status codes in tests.

#### M-03 · Any failure of the start-up session check signs the user out
- **Category:** Reliability · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** `AuthContext.jsx:47-51` removes the token on *any* error from `/auth/me`.
  Reproduced: one 503 on `/auth/me` → redirected to `/login`, token deleted.
- **Impact:** Offline starts, redeploys and Render cold starts log users out.
- **Recommendation:** Remove the token only on 401; otherwise keep it and show a retry /
  offline state.

#### M-04 · Changing the password silently ends the current session
- **Category:** Auth UX · **Confidence:** CONFIRMED · **Effort:** S
- **Evidence:** `passwordChangedAt = now − 1 s` (`User.js:134-135`) invalidates the tab's own
  token; `changePassword` returns no new token (`authController.js:428`). Reproduced with a
  2.5 s-old token: change → 200, next request → 401 "Session expired".
- **Recommendation:** Return a fresh JWT from `PUT /auth/password`, store it client-side, and
  tell the user other devices were signed out.

#### M-05 · Client has no security headers; a 30-day, non-revocable token lives in localStorage
- **Category:** Security — client hardening · **Confidence:** LIKELY · **Effort:** S
- **Evidence:** `client/vercel.json` sets only a font `Cache-Control`; no CSP,
  `frame-ancestors`/X-Frame-Options, `nosniff`, Referrer-Policy or Permissions-Policy;
  `index.html` has no CSP meta. The JWT is in `localStorage` (`api.js:10`), valid 30 days
  (`authController.js:11`), and logout is client-side only.
- **Impact:** Any future XSS (including via a dependency) reads the token; destructive
  Settings actions can be framed (clickjacking).
- **Recommendation:** Add a `/(.*)` headers block (CSP listing exactly the API and the content
  hosts, `frame-ancestors 'none'`, `nosniff`, `strict-origin-when-cross-origin`,

#### M-06 · Abuse controls are thin: XFF-dependent keys, no account lockout, no chat budget
- **Category:** Security — abuse · **Confidence:** CONFIRMED (local) · SUSPECTED (production) · **Effort:** S–M
- **Evidence:** in production `app.set('trust proxy', 1)` (`app.js:10-12`). On the isolated
  production-mode stack (no proxy in front) 12 wrong logins from one client → `401×10, 429×2`,
  but with a rotating `X-Forwarded-For` → `401×12` (bypass). On Render this is safe **only if**
  exactly one proxy hop appends the client IP; with an extra hop (e.g. a CDN) everyone shares
  one bucket instead. Limits are per IP only (no per-account lockout; shared NATs in
  mosques/schools hit the 300/15 min API limit); login and register share one bucket. Chat:
  20 req/5 min per user but no global budget, no `max_tokens`, no request timeout
  (`chatController.js:149-152`), and new accounts are free to create.
- **Recommendation:** Verify `req.ip` in production (log it once); set `trust proxy` to the
  real hop count or Render's documented value. Add per-account failed-login backoff; key the
  API limiter on user id for authenticated routes; set `max_tokens`, a 20 s timeout and a
  global daily chat budget; add the express-rate-limit `validate` checks to tests.

#### M-09 · Mobile performance of the signed-in app and the reader
- **Category:** Performance · **Confidence:** CONFIRMED (Lighthouse 12, simulated mobile, median of 3; Vercel-like gzip host) · **Effort:** M

## 5. Decisions worth revisiting (Phase 2 reconciliation)

Settled decisions recorded in `docs/IMPROVEMENT_PLAN.md` were respected and **not**
re-reported: fit-to-window, `e.code`/`e.key` shortcut matching, the hefzmoyaser/spa5k
edition split (on *quality* grounds), the shared spread undo stack, focus mode removal,
range-band painting, and the two accepted limitations (same-day half-page undo, straddling
verse annotation). These deserve a second look on evidence:

1. **UTC as everyone's day** (CODE_GUIDE §10 "acceptable for this app"). The target audience is
   concentrated at UTC+2 … +9; for South-East Asia the day rolls after Fajr. Streaks and rest
   days — the motivational core — shift by hours. Recommend per-user time zones (M-16).
2. **"No LFS (Vercel serves 48 MB of static fonts fine)"** (log, 2026-07-03). Technically true,
   but committing the fonts to a *public* repo is the main licensing exposure (H-04).
3. **Aysar at-Tafasir via hefzmoyaser** (settled on content quality). Quality was measured
   carefully; permission was not. A private backend of another product with no terms is a
   legal and availability risk regardless of quality (H-04, M-18).
4. **Runtime glyph data from the legacy quran.com API** (Stage 1). The project already ships
   two committed derived datasets; the per-page glyph data is the one remaining hard
   runtime dependency of the core feature (M-18) — subject to H-04 permissions.
5. **30-day, non-revocable JWT in localStorage** (Part 1 S6 "acceptable at this scale").
   Acceptable only with a CSP; there is none (M-05).
6. **Whole-set replace for `PUT /progress/memorized`** (Stage 7). Fine for an editor that has
   just loaded the truth; unsafe as the Library's untick path and on stale state (H-02).
7. **"Lighthouse A11y 92–96" contrast backlog left unprioritised** (open queue). axe shows
   these are WCAG AA failures on every app page, not polish (M-11).

## 8. Cross-cutting UX notes (high level only)

- Silent failure is the dominant UX problem: several screens show "nothing to do" or an
  empty list when the network failed (H-02, M-14). An honest error + Retry pattern, used
  everywhere, would remove a class of confusion and data loss.
- Destructive one-tap actions without undo: the memorized tick removes review history
  (Library), "Reset progress", account deletion. Bookmarks and to-dos already have Restore
  toasts — extend the pattern.
- Arabic users see English server errors and some untranslated labels (L-08).
- Mobile sidebar edge tabs overlap at 390 px (already in the open queue).

## 9. Method, tools and limits

- **Phase 0 inventory:** `git ls-files` (792 files). **Phase 1:** every application file read
  in full — server by the lead auditor; client split across five area reviews whose
  file-level notes are merged ([manifest](audit/coverage-manifest.md)). The plan's progress
  log was read only after the independent pass. **Phase 3:** isolated stack — the real
  `server/app.js` on `mongodb-memory-server` (test, development and production modes, random
  JWT secret, no dotenv, no Groq key), a production client build served by `vite preview`
  and by a Vercel-like gzip host, headless Chrome 155 via Playwright-core.
- **Tools used:** npm audit/outdated, a secret scan of the working tree and all 343 commits
  (gitleaks unavailable — targeted pattern search, values redacted), Lighthouse 12.3
  (mobile + desktop, median of 3; 5 for `/library`), axe-core 4.10 (light + dark), sourcemap
  bundle attribution, Node's test-runner coverage, Mongo `explain()`, 4×-CPU CDP traces,
  fp-check (Trail of Bits) as the false-positive gate, and the Trail of Bits audit approach
  (context building, variant analysis — H-02 groups five variants of one root cause).
  Lighthouse, axe-core and Playwright-core were installed into a scratch folder, not the
  project.
- **Not available:** the Claude Security scan pipeline (needs the Workflow tool, absent in
  this session), Semgrep and CodeQL (not installed; equivalent manual review done). The
  chatbot's model behaviour was not exercised (no Groq key on the isolated stack, by design);
  its server-side validation, context isolation and client rendering were.
- **Limits:** no production measurements (by rule); Render's proxy chain (M-06) and Vercel's
  default headers are inferred; licensing conclusions are research, not legal advice.
